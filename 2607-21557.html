OpenForgeRL is most consequential as infrastructure: it shows how real deployment harnesses can run rollouts while a standard RL backend receives reconstructed training samples, and it backs that idea with unusually broad evidence across Claw, MCP, browser, and desktop GUI agents. Paper overview

OpenForgeRL tackles a practical bottleneck in agent training: modern agents often depend on elaborate inference harnesses for multi-turn reasoning, tool use, browser control, desktop interaction, and access to external systems, while reinforcement learning infrastructure usually expects clean prompt-response training samples.

The paper proposes a proxy plus Kubernetes-orchestrator framework. Real deployment harnesses run rollouts in their native environment, model calls are proxied, trajectories are reconstructed, and a standard RL stack such as veRL receives the resulting samples. This makes the contribution primarily a systems-method paper rather than a new RL algorithm.

The empirical study spans Claw/tool-use and GUI/browser/computer-use agents. The paper reports gains for OpenForge-Claw on ClawEval, QwenClawBench, and MCPAtlas, and for OpenForge-GUI on OSWorld-Verified, Online-Mind2Web, and WebVoyager. It also includes cross-harness and SFT/RL behavior analyses, which makes the work more informative than a narrow benchmark table.

The central claim is that harness-native training can generalize across agent environments without forcing researchers to rewrite each deployment harness as a special-purpose training loop. That claim is important and plausible, but its current strength depends on artifact release, statistical validation, and clearer compatibility boundaries.

Key strengths

High-value problem selection. Training agents inside their real inference harnesses is a timely and important problem because harness behavior increasingly determines what an agent can actually do in deployment.

Clean systems abstraction. Proxying model calls, reconstructing trajectories, and feeding standard RL backends is a practical bridge between complex agent harnesses and existing reinforcement learning infrastructure.

Broad validation across agent domains. The paper covers Claw, MCP, browser, and desktop GUI environments, which gives the study more breadth than most close prior work on harness-native or proxy-based training.

Useful behavioral analysis beyond headline metrics. The cross-harness and SFT/RL analyses help explain how training changes behavior, rather than reducing the paper to leaderboard-style point estimates.

Practical implementation detail. Reporting resource caps, timeouts, task counts, training times, and data synthesis costs makes the systems contribution easier to evaluate and gives future implementers concrete design anchors.

Key concerns and constructive suggestions

The main gains lack uncertainty estimates. The benchmark tables report point estimates without confidence intervals, repeated seeds, or significance tests, even though agent evaluations are stochastic and close comparisons can be sensitive to sampling. To address this, the authors should rerun the main evaluations with repeated sampling or training seeds where feasible and report bootstrap confidence intervals over tasks.

Reproducibility is weak without public artifacts. For an implementation-centered systems paper, the absence of an accessible official repository, data, models, task IDs, and evaluation scripts makes the central claims difficult for independent users to verify. To address this, the authors should release code, proxy and orchestrator modules, training configs, task IDs, generated environments, verifier scripts, checkpoints, and a small one-command smoke test.

Reward and verifier dependencies need independent validation. Generated task verifiers and LLM-judge rewards are central to the pipeline, but the paper does not yet provide enough evidence about false positives, false negatives, judge agreement, or sensitivity to judge choice. To address this, the authors should human-label a stratified sample of tasks and outcomes, measure verifier error rates, and stress-test synthetic verifiers with adversarial near-miss trajectories.

Novelty positioning should account for Polar. Polar appears to overlap with the broad proxy and trajectory reconstruction idea, so framing OpenForgeRL as wholly unique on that axis is less defensible than emphasizing breadth, integration, task synthesis, and behavior analysis. To address this, the authors should add a direct comparison or compatibility mapping against Polar under a shared task or minimal harness setting.

The “any harness x any environment” claim needs boundaries. The evidence spans several important domains, but it does not prove that arbitrary harnesses and environments satisfy the framework's assumptions. To address this, the authors should add a compatibility matrix documenting model-call API assumptions, reward availability, container requirements, timeout semantics, unsupported harness patterns, and representative failure cases.

Presentation polish still matters for a systems-method paper. Typos and naming inconsistencies can make implementation details harder to follow and reduce confidence in exact reproduction. To address this, the authors should run a focused editorial pass aligning terminology, table labels, model names, and artifact names across the main text and appendix.

What would most improve this paper

1. Make the work reproducible. Release the OpenForgeRL implementation, proxy/orchestrator modules, examples, training configs, generated tasks, verifier scripts, model checkpoints, evaluation scripts, and exact task IDs, plus a small public smoke test that exercises the end-to-end path.

2. Add statistical rigor to the headline results. Report repeated evaluations, bootstrap confidence intervals, and judge sensitivity analyses so readers can distinguish robust gains from sampling noise.

3. Validate reward and verifier dependencies. Add human agreement studies, verifier false-positive and false-negative estimates, and adversarial near-miss tests for generated verifiers and judged browser outcomes.

4. Sharpen novelty through direct comparison. Compare with Polar or add a shared minimal benchmark that clarifies what OpenForgeRL contributes beyond the general proxy/reconstruction pattern.

5. Document compatibility limits. Provide an integration matrix and negative cases so independent users know which harness patterns are supported, which assumptions are required, and where author intervention is still likely.
