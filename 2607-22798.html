StateAct makes a strong practical case for grounding long-horizon computer-use agents in program state rather than screenshots alone. Its most consequential strength is the coherent harness: state-first action, rare GUI delegation, structural finish checks, and context management all serve the same diagnosis of hidden-state failures. The most important improvement direction is auditability — release the implementation details, add uncertainty analysis, validate the verifier boundary, and sharpen the comparison to adjacent state/code/hybrid agent systems.

Paper overview

StateAct addresses a practical failure mode in computer-use agents: screenshots are only a lossy rendering of the underlying application state. Files, DOM structure, spreadsheet formulas, hidden rows, backend data, and persistence details can matter more than pixels for long-horizon desktop tasks.

The paper proposes a code-first, multi-agent harness. A main agent directly inspects and modifies program state through code, while a dedicated GUI subagent handles the smaller set of subgoals that truly require visual interaction. The same emphasis on state also informs verification: an independent finish gate checks the saved result for structural failures before task completion is accepted by the harness.

The reported OSWorld 2.0 results are promising because they use the same model backbone in the reference and StateAct settings, which makes the harness contribution easier to isolate than a model-to-model comparison. The paper is strongest as a systems argument: many long-horizon failures are not primarily screenshot perception failures, and agent infrastructure should expose and verify the program state that actually defines success.

Key strengths

Clear state-vs-pixel framing. The paper gives a crisp reason why screenshot-only agents struggle: different application states can render to similar pixels, while the state that determines task success may live in files, formulas, backend objects, or DOM elements. This framing is simple, reusable, and directly tied to the method.

Coherent harness design. The architecture aligns action, verification, and context management around the same long-horizon state problem. The GUI subagent is used sparingly, which makes the design feel concrete rather than rhetorical: visual interaction remains available, but it is no longer the default substrate for every step.

Same-backbone empirical evidence. Comparing the reference harness and StateAct with the same underlying model better isolates the value of the harness itself. The reported gains therefore support a useful systems claim: better access to program state can improve computer-use agents even without changing the base model.

Honest verifier diagnostics. The paper does not treat its finish gate as a full correctness oracle. It acknowledges that structural checks can pass tasks with wrong values, which is exactly the right boundary to surface for future verifier work.

Cost-aware evaluation. Reporting task performance alongside cost is important for agent systems, where long episodes and visual interaction can dominate deployment feasibility. The paper's cost framing makes the efficiency advantage of state access part of the scientific claim rather than an afterthought.

Key concerns and constructive suggestions

Reproducibility is insufficient for an implementation-based paper. The central contribution is a harness, but no public implementation package was detected for the exact paper. This limits confidence in prompts, tool interfaces, routing behavior, context handling, cost accounting, and failure labels. To address this, the authors should release the harness, prompts, tool schemas, environment setup, OSWorld 2.0 configuration, metric scripts, cost-accounting code, finish-gate prompts, and sample trajectories; if some components cannot be released, a reduced runnable harness would still materially improve auditability.

Main results need uncertainty analysis. The benchmark evidence is reported as point estimates, which makes it hard to judge effect size and robustness across a modest task set. To address this, the authors should add bootstrap or Wilson intervals, paired task-level tests, partial-score variance, and per-task delta plots that show where the harness helps and where it does not.

Closest prior art needs sharper differentiation. The paper cites adjacent code-action, hybrid GUI/state, and verifier-centered systems, but the distinction from CodeAct, CoAct-1, UFO2, MCPWorld, OpenComputer, and the earlier StateAct paper remains underdeveloped. To address this, the authors should add a design matrix and a concise comparison section that separates novelty in routing, state access, verification, context sustain, and empirical diagnosis.

The finish gate should remain framed as structural verification. The finish gate is valuable, but it cannot validate general value correctness, and the paper's own analysis shows residual wrong-value tasks can pass. To address this, the authors should consistently label the gate as structural, report pass/fail behavior by error type, and test hybrid structural/value-aware verifier variants on a subset of tasks.

The manual failure audit needs a published protocol. The failure taxonomy is useful, but the labeling process, rubric, examples, and annotator agreement are not described in enough detail to make the diagnosis independently assessable. To address this, the authors should publish category definitions, representative trajectories, annotation instructions, and multi-annotator checks.

What would most improve this paper

1. Release a reproduction package. The paper's method is the harness, so the highest-impact improvement is making that harness inspectable: code, prompts, tool schemas, operating constraints, benchmark setup, traces, metric scripts, and cost accounting.

2. Add uncertainty and paired task-level analysis. Confidence intervals, paired tests, partial-score variance, and task-level deltas would make the reported gain easier to interpret and would show which task types benefit from state-first action.

3. Publish exact protocol details. An appendix with prompts, routing policy, finish-gate prompt, retry behavior, compaction policy, and tool contracts would turn the method from a persuasive architecture into something other researchers can implement and critique.

4. Calibrate novelty against adjacent systems. A direct comparison to prior state/code/hybrid agent systems, including disambiguation from the earlier StateAct work, would strengthen the paper's scholarly positioning without weakening the contribution.

5. Extend the verifier and audit story. Reporting structural versus value-correctness failures, releasing audit rubrics, and testing value-aware verifier variants would turn the limitation discussion into a clearer research agenda.
